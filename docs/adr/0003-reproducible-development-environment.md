# 0003. Воспроизводимое окружение и dev-server для редакторов

[English version](0003-reproducible-development-environment.en.md)

Статус: принято (2026-11-03)

## Контекст

Проекту нужны Rust, bun, совпадающий `wasm-bindgen-cli` и нативные библиотеки. Дублирование версий и пакетов в CI, документации и настройках редакторов ведёт к расхождениям. Браузерной отладке нужен запущенный Vite; ручной запуск менял поведение конфигурации по сравнению с апстримом.

## Решение

Для каждого входа окружения используется один источник: `rust-toolchain.toml` для Rust, `package.json` для bun, `Cargo.lock` для wasm-bindgen, `tools/system-deps/debian.txt` для пакетов Debian и совпадающие закреплённые версии cargo-deny в workflow.

`tools/doctor` проверяет окружение без установки и запускает тесты согласованности репозитория. `tools/setup` предоставляет основной локальный путь настройки: `bun run setup` устанавливает JS-зависимости по lockfile и проверяет CLI/web-окружение, а `bun run setup --install` дополнительно устанавливает Rust toolchain и `wasm-bindgen-cli`. Помощник не выполняет `sudo`; desktop-зависимости остаются отдельным явным шагом. Необязательный `.devcontainer/` сохранён как изолированная альтернатива и использует тот же список пакетов и файлы тулчейна, с именованными томами для артефактов.

### Почему нужны оба способа

Setup и devcontainer не дублируют друг друга, а закрывают разные сценарии:

- **Setup лучше для постоянной работы на хосте.** Он не требует Docker, использует привычные редактор и системные инструменты, поддерживает нативное окно Tauri и сборки для host-платформы, а после настройки быстро повторно проверяет окружение.
- **Devcontainer лучше для чистого и воспроизводимого старта.** Он содержит системные библиотеки и закреплённый toolchain, уменьшает влияние различий между машинами и позволяет отделить окружение проекта от остальной системы. Это полезно для первого знакомства, работы на неподготовленной машине и проверки проблем, зависящих от окружения.
- **Совместное использование не создаёт двух независимых конфигураций.** Оба пути читают одни файлы версий и список системных пакетов, а `doctor` одинаково проверяет результат. Setup снижает стоимость ежедневной работы, devcontainer ограничивает риск расхождения сред; ни один из них не заменяет проверки на реальном хосте и в чистом окружении одновременно.

`tools/dev-server` предоставляет `dev:web:start` и `dev:web:stop`. Он переиспользует работающий сервер, собирает WASM перед запуском Vite, ждёт готовности, хранит PID и логи в `target/` и оставляет сервер для следующих сессий отладки. Сценарии launch в Zed и VS Code вызывают одну задачу; attach не управляет сервером.

## Альтернативы

- **Дублировать инструкции.** Просто вначале, но версии и пакеты расходятся.
- **Только devcontainer.** Воспроизводимый Linux, но нет нативного окна и сборок на macOS/Windows.
- **Заменить devcontainer setup-помощником.** Локальный сценарий удобнее, но не даёт изолированного Linux-окружения и не устанавливает системные зависимости автоматически.
- **Ручной запуск Vite.** Меньше инструментов, но ненадёжный и неодинаковый запуск из редакторов.
- **Новый сервер на каждую сессию.** Изоляция здесь не нужна, а конфликты портов и повторные сборки WASM неизбежны.

## Последствия

- (+) CI, локальная настройка, контейнер и редакторы используют согласованные входы.
- (+) Браузерная отладка запускается одним действием и переиспользует существующую работу.
- (−) Помощники и consistency-тесты нужно поддерживать при развитии workspace.
- (−) Контейнер большой и не заменяет проверки на хосте.
