# Архитектура Specialist Emulator

[English version](architecture.en.md)

## Назначение документа

Документ фиксирует текущие границы проекта и целевую архитектуру полноценного эмулятора «Специалиста». Планы поэтапного развития находятся в [roadmap.md](roadmap.md).

Слова «реализовано» относятся к коду в репозитории. Разделы о целевой архитектуре описывают предлагаемые решения и не означают, что соответствующие компоненты уже существуют.

## Цели и ограничения

Основные цели:

- одно детерминированное ядро для CLI, браузера, нативного приложения и отладчика;
- воспроизводимое поведение конкретных конфигураций «Специалиста», а не только абстрактного Intel 8080;
- одинаковые результаты выполнения на нативной платформе и в WebAssembly;
- независимый запуск ядра без графического интерфейса;
- отладка программ внутри эмулятора через Debug Adapter Protocol (DAP);
- отладка самого эмулятора обычными нативными инструментами Rust.

Проект не ставит целью перенос всего интерфейса в расширение редактора. Экран, клавиатура и периферия остаются частью приложений эмулятора; Zed использует стандартный интерфейс отладки.

## Общая схема

```text
                         ┌──────────────────────────┐
                         │      specialist-core     │
                         │ CPU · Bus · Machine · RAM│
                         └────────────┬─────────────┘
                                      │
              ┌───────────────────────┼────────────────────────┐
              │                       │                        │
       specialist-cli       specialist-core-wasm       native/Tauri IPC
              │                       │                        │
        терминал                 web-адаптер              desktop-адаптер
                                      │                        │
                                      └──────────┬─────────────┘
                                                 │
                                     общий Solid UI + core-api

Zed → specialist-zed → stdio/DAP → specialist-dap → specialist-core
```

`specialist-dap` и интеграция с Zed относятся к целевой архитектуре. Расширение разрабатывается в репозитории [specialist-zed](https://github.com/Specialist-PK/specialist-zed).

## Текущие компоненты

| Компонент            | Ответственность                                                                                |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `crates/core`        | Intel 8080, регистры, флаги, стек, карты памяти Demo/Monitor 2, порты, `Machine` и видеопамять |
| `crates/core-wasm`   | Тонкая `wasm-bindgen`-граница над `Machine`                                                    |
| `crates/cli`         | Консольный запуск демонстрации, BIN-файлов и внешнего Monitor 2 ROM                            |
| `packages/core-api`  | Независимый TypeScript-контракт `Emulator`, снимки состояния и ошибки                          |
| `packages/core-wasm` | Инициализация WASM и адаптация ядра к `Emulator`                                               |
| `packages/app`       | Общий Solid UI: экран, регистры и управление выполнением                                       |
| `apps/web`           | Точка входа браузерного приложения                                                             |
| `apps/native`        | Точка входа Tauri, нативный IPC и владение `Machine`                                           |
| `tests/e2e`          | Сквозная проверка браузерного интерфейса в Chromium                                            |

Направление зависимостей:

```text
CLI и Tauri → specialist-core
Web         → specialist-core-wasm → specialist-core
Web и Tauri → @specialist/app → @specialist/core-api
```

Обратных зависимостей быть не должно. Общий UI не знает о WASM, Tauri или конкретном приложении.

## Модель выполнения

### Процессор и память

`Machine` объединяет CPU, системную шину, карту памяти выбранной конфигурации и счётчик циклов. Реализованы 256 базовых опкодов Intel 8080 и 256 портов ввода-вывода. Видеопамять начинается с `0x9000`, экран имеет размер 384 × 256 пикселей.

Режим `Demo` сохраняет плоскую RAM для встроенной программы и произвольных BIN-файлов. В режиме `Monitor2` диапазон `0000–BFFF` является записываемой RAM, а `C000–D7FF` — ROM с запретом записи. Внешний ROM размером `0x1800` загружается с `C000`; выполнение без обязательного ROM возвращает ошибку до первой инструкции. Поведение нераспределённых адресов и системного порта остаётся отдельной задачей.

Доступ к памяти и портам проходит через абстракцию `Bus`. Новые устройства должны подключаться к ней, а не обходить её прямым доступом из CPU.

### Детерминизм

Для одного начального состояния, конфигурации и последовательности внешних событий результат выполнения должен совпадать на всех платформах. Ядро не читает системные часы, файловую систему или DOM и не использует платформенную многопоточность.

Время задаётся тактами и событиями машины. Аудио- и видеовывод являются потребителями состояния ядра и не должны влиять на результат исполнения.

Счётчик циклов имеет тип `u64`. На TypeScript-границах он передаётся строкой и нормализуется адаптером, чтобы не потерять точность.

### Остановка и безопасность выполнения

Пакетный запуск имеет лимит инструкций. Его нельзя убирать: без лимита загруженная программа может заблокировать CLI, WASM-поток или нативный вызов.

Все адреса и диапазоны проверяются на платформенных границах. Загрузка BIN не должна молча переписывать память за пределами 16-битного адресного пространства.

## Целевая модель машины

Первая эталонная конфигурация определена в [reference-machine.md](reference-machine.md) и [ADR-0011](adr/0011-reference-specialist-configuration.md).

Для перехода от демонстрационного компьютера к конкретным моделям предлагается разделить:

- `Cpu` — исполнение Intel 8080;
- карту памяти — RAM, ROM, видеопамять и окна переключения;
- контроллеры периферии — клавиатура, таймер, лента, звук и дисковые интерфейсы;
- видеоконтроллер — чтение памяти, раскадровка и формирование кадра;
- `MachineConfig` — идентификатор модели, карта памяти, частоты и набор устройств;
- `Machine` — композиция компонентов и детерминированный цикл выполнения.

Конфигурации должны быть данными или небольшими фабриками, а не разрозненными условными проверками внутри CPU. Названия моделей и их особенности нужно подтверждать источниками; непроверенные предположения помечаются в документации.

ROM загружается отдельно от ядра. В репозиторий добавляются только материалы с подтверждённым правом распространения.

## Платформенные адаптеры

### WebAssembly

`crates/core` остаётся совместимым с `wasm32-unknown-unknown`. `crates/core-wasm` только экспортирует возможности `Machine`; дублирование логики процессора или устройств в адаптере запрещено.

Сгенерированный каталог `packages/core-wasm/pkg` не является исходным кодом и не коммитится.

### Tauri

Tauri владеет одним `Machine` через `AppState` и `Mutex`. Команды принимают и возвращают типизированные данные, а TypeScript-адаптер реализует тот же `Emulator`, что и WASM.

При добавлении команды одновременно обновляются команда, регистрация Specta, список в `build.rs`, обе capabilities и сгенерированные привязки.

### CLI и встраивание

CLI использует ядро напрямую и не зависит от Bun, Vite или Tauri. Этот же путь является основой для тестовых стендов и будущего DAP-процесса.

## Архитектура отладки

Нужно различать две задачи:

1. **Отладка программы для «Специалиста»**. Выполняется через собственный DAP-адаптер, управляющий `Machine`.
2. **Отладка реализации эмулятора**. Выполняется через CodeLLDB или другой нативный Rust-отладчик; существующий `.zed/debug.json` относится именно к этой задаче.

Целевая схема программной отладки:

```text
┌─────┐   extension API   ┌────────────────┐   stdio + DAP   ┌────────────────┐
│ Zed │ ────────────────→ │ specialist-zed │ ──────────────→ │ specialist-dap │
└─────┘                   └────────────────┘                 └───────┬────────┘
                                                                      │
                                                             ┌────────▼────────┐
                                                             │ DebugController │
                                                             │ + Machine       │
                                                             └─────────────────┘
```

`specialist-dap` должен находиться в workspace эмулятора и использовать `specialist-core` напрямую. Расширение Zed не содержит второй реализации эмулятора и не реализует DAP поверх нестабильного TypeScript IPC.

### Состояния отладочной сессии

Минимальная модель: `launch` создаёт машину, загружает программу и оставляет её остановленной или запускает до первой точки останова. DAP-адаптер последовательно обрабатывает команды и публикует события остановки и завершения.

Первоначально поддерживается один эмулируемый процесс и один логический поток. `attach` к уже работающему экземпляру появляется только после определения транспорта и владения сессией; нельзя имитировать attach созданием новой машины.

### Отладочные операции

Базовый контракт:

- установка и снятие точки останова по 16-битному адресу;
- остановка перед исполнением инструкции по адресу точки;
- продолжение, пауза, шаг по инструкции и сброс;
- регистры, флаги, стек и чтение памяти;
- дизассемблирование вокруг PC;
- корректное завершение сессии без оставшихся процессов.

Intel 8080 не предоставляет достаточной информации для надёжного восстановления цепочки вызовов произвольной программы. Начальная версия должна показывать одну текущую псевдорамку вместо выдуманного стека вызовов. Анализ CALL/RET можно добавить позже как отдельную, явно приблизительную функцию.

### Источники и адреса

DAP работает с исходными файлами и адресами. Для BIN без отладочной информации основным режимом является дизассемблер. Связывание с исходным ассемблером требует отдельного формата карты адресов или символов; этот формат должен быть версионируемым и независимым от Zed.

## Совместимость контрактов

Стабильными точками интеграции являются:

- публичный API `specialist-core` для Rust-компонентов;
- TypeScript-интерфейс `Emulator` для приложений;
- исполняемый файл `specialist-dap`, его аргументы и JSON Schema сценария для Zed;
- версионируемые форматы конфигурации машины, символов и снимков состояния.

Изменение DAP-конфигурации требует синхронного обновления схемы, документации и совместимости с `specialist-zed`. Номер версии адаптера должен быть доступен расширению для диагностики.

## Проверка архитектуры

Минимальные уровни проверки:

1. Модульные тесты CPU, памяти и устройств.
2. Общие исполняемые тестовые векторы для нативного ядра и WASM.
3. Интеграционные тесты Tauri IPC и TypeScript-контрактов.
4. Сквозные тесты интерфейса.
5. Протокольные тесты DAP: initialize → launch → breakpoint → continue → variables/stackTrace → terminate.
6. Сквозной сценарий с настоящим Zed и dev-расширением.

Для аппаратной совместимости полезно использовать общие тестовые программы и результаты с [special20k](https://github.com/Specialist-PK/special20k), но расхождения нужно сначала сверять с документацией реальной машины, а не автоматически считать одну реализацию эталоном другой.

## Принятые решения

- Ядро остаётся в `specialist-emulator`; расширение редактора не владеет эмуляцией.
- Для подключения к Zed используется внешний процесс и стандартный DAP.
- Браузерный и нативный UI разделяют контракт, но не платформенные адаптеры.
- Сначала строятся проверяемая модель машины и отладочные примитивы, затем редакторная интеграция.
- Точность и воспроизводимость важнее скорости; оптимизации не должны менять наблюдаемое поведение без обновления тестов и документации.
