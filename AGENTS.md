# AGENTS.md

[Русская версия](AGENTS.ru.md)

Instructions for AI agents working in this repository. See `README.md` for the project overview.

## Context

This project inherits the learning-oriented workflow of `another-useless-app`: understanding decisions matters as much as the emulator itself.

- Work in small steps: one idea at a time, verified by builds and tests.
- Explain the chosen decision, its rationale, and the alternative.
- Read `docs/adr/` before changing architecture. Record significant decisions in a new ADR using the format in `docs/adr/0001-*`; replace accepted ADRs with new ones instead of rewriting them.
- User experience: TypeScript and React — high; Rust, Solid, Tailwind — low. Apply best practices in these areas and explain non-trivial differences through React/TypeScript analogies.
- Solid components run once, signals are functions, destructuring props breaks reactivity, and `Show`/`For` replace React-style conditional rendering and `map`. Rust uses `Result` instead of exceptions; a trait is not identical to a TypeScript interface.
- Communicate with the user in Russian. Code, identifiers, and commits are in English.

## Structure

- `crates/core` — platform-independent i8080 core.
- `crates/core-wasm` — thin `wasm-bindgen` boundary only.
- `crates/cli` — console application (`specialist` binary).
- `packages/core-api` — dependency-free TypeScript `Emulator` contract.
- `packages/core-wasm` — WASM build and TypeScript implementation of the contract.
- `packages/app` — shared Solid UI; the core comes from `CoreContext`.
- `apps/web` and `apps/native` — independent entry points that connect concrete cores.
- `tools/doctor` — read-only environment diagnostics and consistency tests.
- `tools/boundaries` — declared dependency checks with rules in `rules.json`.
- `tools/ci` — tested selection of CI jobs from changed files.
- `tools/dev-server` — background Vite startup, readiness checks, and shutdown for editor debugging.
- `tools/system-deps` — the single Debian/Ubuntu system package list.
- `tests/e2e` — web E2E in a real Chromium browser.

## Hard architecture rules

1. `crates/core` must not depend on DOM, Tauri, filesystem APIs, or dependencies incompatible with `wasm32-unknown-unknown`.
2. `crates/core-wasm` contains no separate emulator implementation.
3. `packages/core-api` does not depend on UI or platforms.
4. `packages/app` knows only `core-api` and receives the core through `CoreContext`.
5. Applications do not depend on each other. Only entry points connect concrete cores.
6. CLI does not require bun/Vite; web does not require Tauri; desktop uses the native core through IPC.
7. A new core capability requires an `Emulator` method, both implementations (WASM and IPC), and real execution tests.
8. `packages/core-wasm/pkg` is generated by `bun run build:wasm` and is not committed. The `wasm-bindgen` crate and CLI versions must match.
9. `apps/native/src/bindings.ts` is generated by `bun run update:bindings`; never edit it manually. New Tauri commands also go into `build.rs` and both capabilities.
10. Dependency boundaries are data in `tools/boundaries/rules.json`. Update them with architecture changes and verify new rules by intentionally violating a real manifest.
11. Run `bun run deny` after every `Cargo.toml`/`Cargo.lock` change. Exceptions require a reason; do not add OpenSSL/native-tls or packages outside crates.io.
12. Do not add ROMs or third-party programs without a confirmed redistribution right.

Before finishing, run `bun run format:check`, `bun run format:check:rust`, `bun run lint`, `bun run test:rust`, `bun run typecheck`, and `bun run test`. For core or WASM changes also run `bun run check:wasm` and `bun run test:wasm`; for web changes run `bun run build:web` and `bun run test:e2e`; for Tauri changes run `bun run test:native` and `bun run build:native -- --no-bundle`. Explicitly report anything that could not be checked.

`bun run dev:native` opens a real window: do not run it without a user request. E2E uses system Chromium, supports `CHROME_PATH`, skips when no browser is available locally, and fails when `E2E_REQUIRE_BROWSER=1`.

## Environment

`bun run doctor` reports missing tools and never installs anything. Versions have one source:

- Rust — `rust-toolchain.toml`;
- bun — `package.json` (`packageManager`);
- `wasm-bindgen-cli` — `Cargo.lock`;
- Debian system packages — `tools/system-deps/debian.txt`;
- cargo-deny — matching pins in both workflow files.

Do not duplicate these versions in CI or scripts. Node.js is not required. The optional devcontainer in `.devcontainer/` uses the same sources and named volumes for build artifacts.

## Stack and versions

- bun workspaces; dependency versions are pinned in the root `package.json` catalog. Add packages with `"catalog:"`.
- Solid 2 RC and TypeScript 7 native `tsc`; consult local sources for APIs that differ from Solid 1 or React.
- Tailwind 4 CSS-first configuration lives in `packages/config/theme.css`.
- Rust edition 2024, resolver 3. Shared crate dependencies use `[workspace.dependencies]`.

## Style

- Rust: `cargo fmt`, library errors through `thiserror`.
- TS/TSX/JSON/CSS: `oxfmt`; lint with type-aware `oxlint`.
- Generated files are not edited, formatted, or linted manually.
- TypeScript is strict and uses `verbatimModuleSyntax` and `noUncheckedIndexedAccess`.
- Comments explain “why”, not “what”. Ordinary `//` comments are Russian. Rustdoc and TSDoc are English for generated declarations and IDE quick info.
- Documentation is bilingual: English is canonical (`.md`), Russian is next to it (`.ru.md`), with cross-links. Special GitHub filenames may contain both languages inline. Existing legacy documents are migrated in separate PRs.
- Existing project code and documentation remain MIT-licensed; changing documentation licensing is a separate decision.

## Editor workflow

Workspace settings for VS Code and Zed must keep shared scenarios and tasks in sync. Web launch configurations call `web: ensure dev server`; attach configurations do not start or stop it. The helper reuses an existing server, builds WASM before starting a new one, waits for readiness, and keeps the server for subsequent sessions. Stop it with `web: stop dev server`.

## GitHub workflow

Work happens through issues and pull requests. GitHub Issues are the source of truth for plans; the pinned Roadmap issue provides the overview.

1. **Issue.** Every task starts with an issue (`Task` or `Bug` template). Create one if needed and link it to the Roadmap.
2. **Branch.** One branch per issue from fresh `main`: `<type>/<summary>`. No direct commits to `main`.
3. **Commits.** Small Conventional Commits in English (`feat:`, `fix:`, `docs:`, `chore:`, `ci:`), one idea each.
4. **Pull request.** Fill the template and include `Closes #N`. Title follows commit style in English; description is in Russian. List skipped checks honestly under “Not verified”.
5. **Merge.** Squash only, after the aggregate `ci` check is green. Path-skipped jobs count as success. The branch is deleted automatically. Adding an OS or job does not require branch-protection changes. Update `tools/ci/src/select.ts` and its tests when adding directories or dependencies between project areas.

User confirmation is required for commits, pushes, creating/closing issues and PRs, and merging. A request to perform one named action does not authorize merging or other actions.

Do not add `node_modules`, `target`, `dist`, or generated WASM output to the repository.
